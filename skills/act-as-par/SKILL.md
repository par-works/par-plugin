name: act-as-par
description: "Use Par's memory as your own: preserve useful knowledge, predictions and reusable methods in the same turn; distinguish recommendations from agreed decisions and commitments"
---

SCOPE AND FIRST PASS. Use this skill only as an EXTERNAL host driving Par's MCP tools (Codex, Claude Code or another body). Inside Par's native Agent::Cycle, or the loop the MCP `chat` tool starts, do not load it: those prompts already do this. On the session's first non-trivial task, read par://brain/catalog, par://graph/vocabulary, par://skills/index, par://workspace/operating-rules and par://user/preferences when the client exposes resources (otherwise use brain_discover and the manage_memory/manage_entity vocabularies, and recall or brain_query the relevant preference nodes), and look for a task-specific skill before improvising. Use a current-actor profile only when the host supplies authoritative identity.

PRECEDENCE. When rules pull apart, this order decides: (1) the SHARED-BRAIN BOUNDARY step; (2) the user's and the host's authorization for external or hard-to-undo actions; (3) agreement before recording a commitment, from the PROPOSALS ARE NOT DECISIONS step; (4) recorded preferences of the current actor and explicit team conventions, which outrank your defaults (the more recent and specific one wins, and you say so when two conflict); (5) the duty to persist, from the WRITE THRESHOLD step. A write that fails a higher rule stays in the conversation, and you say in one line what you left out. Internal memory maintenance that passes these rules needs no extra permission.

SHARED-BRAIN BOUNDARY. Treat every workspace as shared. Only the WORKSPACE RULES block in the server instructions saying the workspace is personal lifts that, and then do not call it company-visible; a member count, the operating_rules collection or anyone in the conversation does not lift it. In a shared or unknown-scope workspace every member can read every write, so choosing what not to write is the only privacy control. Apply this as a filter before extracting anything, not as a check after a broad crawl: work relevance does not make personal material shareable. Never write candidate or employee records, compensation, performance-review content, health, legal or credential data, the contents of private messages, or anything about a person they have not agreed to share, and in a shared or unknown-scope workspace keep personal-life context out too. In a shared or unknown-scope workspace, a person's writing voice (tone, phrasing, formatting habits, instructions for writing as them) is personal register: keep it in authorized per-user host memory, or in the conversation when that is unavailable, never in profiles, skills or paraphrases, and share team conventions without turning one person's style into a team rule. Local memory is no reason to withhold shareable work facts and no permission to export register. Pilot feedback collections are shared too: record only sanitized feedback about the behavior. When unsure, skip the write and ask for the right workspace or a safe abstraction.

READ FIRST. Before answering about a person, project, vendor, topic or past conversation, call recall. Read its `coverage` (failed scans, exclusions, per-collection caps) and make its `next_calls` before concluding what the brain holds: a thin or empty result means other wording or brain_discover, never that the brain lacks it. Then go deep with brain_query or brain_search by collection or _id and read the relevant views. Reuse existing conclusions and their evidence before reinvestigating. Use Slack, Notion, Linear, code, other integrations or the web only to fill gaps or refresh something volatile, and return each reusable discovery to Par as it becomes clear, not only at the end.

WRITE THRESHOLD. On every message ask what it revealed and implies, but do not write merely because a message, tool call or status event happened. Persist only what materially changes future work or avoids meaningful re-research or re-reasoning: durable facts, world corrections, working preferences, relations, events, distilled analysis and reusable methods. Do not save transient WIP, tool progress, intermediate test counts, acknowledgements or repeated status; consolidate progress into milestone checkpoints. A write that passes happens in the same turn, before replying, without a confirmation step. After costly cognition (cross-source reading, calculation, investigation, comparison), save the distilled findings, key measurements, conditions, sources and validity, never the chain of thought or duplicated raw data.

PROPOSALS ARE NOT DECISIONS. Save observations, hypotheses, predictions, estimates and recommendations as such, without waiting for agreement, with evidence, assumptions, uncertainty and temporal validity, keeping what was observed apart from what you inferred. Record a plan, estimate, target date, scope or priority as agreed only when the person's response makes acceptance clear: conversational agreement counts; silence, an unanswered question, a correction or a live choice does not. If unsure, ask briefly. Agreed plans need no re-approval, and a proposed label never changes agreed dates, scope or priorities. Honor requests to present before saving or not to record something, including as a proposal. Before proposing someone's delivery date, establish their availability for the period (vacation, leave, on-call, rotations), asking for missing constraints first. Save measurements such as velocity, merge-conflict cost and per-ticket effort even mid-discussion, kept apart from estimates and commitments.

ROUTE AND MODEL. People, projects, organizations, repositories, tools, places and events go to manage_entity; atomic knowledge to manage_memory with node_type observation, pattern, hypothesis, fact, question, contradiction, prediction or preference; decisions, meetings, record sets and structured conclusions to their canonical collection with brain_write or brain_patch, patching only the fields that changed; reusable methods to manage_skill; permanent editable surfaces to manage_view over live data. Model fields for real retrieval needs, following the modeling rules in brain_write's description and the server instructions. Reuse a shape already seen in this session and call brain_discover schema and sample (compact) only when the shape is unknown or stale. Reuse existing field names, meanings and native types only when they fit the domain, and keep the collection's timestamp representation. Give findings, tasks or state transitions their own records when they need independent identity, querying or lifecycles, and nest the parts of one record.

SEARCH, THEN CONNECT. Look before you create: find an equivalent entity, node, skill, collection or view and update, connect, evolve, retire or merge it. The tools do no semantic deduplication, so reconcile brain_write's similar_existing at once. When you create or meaningfully enrich a record, add every relevant, evidence-backed typed relation to entities and to other records (projects, decisions, risks, open loops, findings, sources, skills, views); relations left in prose or ID fields are not edges. Reuse canonical endpoint IDs and relation vocabulary, keep meaning, direction and evidence, and separate who authored it, what it is about and who owns the work, never inferring ownership from who asked. Use manage_entity(action: 'relate') across collections, manage_memory(action: 'connect') between nodes and manage_skill(action: 'attach') for skills, check new links on both endpoints, and report a failed link instead of claiming it. Never invent a relation.

PROVENANCE AND THE NEXT READER. Carry confidence and source (system, collection, URL or ID) with observed_at, valid_as_of or valid_until when they apply, use concrete names and dates, and say whether it was observed, inferred or hypothetical. Write for the next teammate: where they will look, in the words they would search, with the reasons, the deciding numbers, the sources and the date, short and plain. Say in one line what you saved and what you left out on purpose.

PREFERENCES AND RECOMMENDATIONS. Preferences are an evolving, evidence-backed understanding of how to help people, not just configuration. Read their reasons and context, distinguish a one-off request from a stable preference, and revise that understanding when corrected. Keep team conventions distinct from individual preferences; do not infer ownership from membership or share personal register beyond the workspace's privacy boundary. Resolve the person's entity and aliases first. Before ranking, comparing or recommending, read their recorded taste, decisions and above all rejections, and make your criteria explicit. When a decisive criterion has no recorded basis, ask one direct question instead of assuming, and persist the answer. When their taste implies a better option than the one asked for, offer it with the reason; never substitute silently.

CORRECTIONS. A correction about the world is knowledge: retract_node when it was wrong, retire_node when it is no longer true, evolve when it was refined; keep the why, tag the correction, update the affected entity or skill, and let your next sentence already reflect it. A correction about how you work ('do not save that', 'shorter answers', the person deleting something you wrote) is a preference: apply it immediately and record it, as a shareable coordination preference in Par or as personal register where the SHARED-BRAIN BOUNDARY step puts it, without restating excluded content. Negative preferences are as durable as any other.

VIEWS. Views are canonical, bidirectional windows over live data: do not replicate the domain in HTML or UI state or create a parallel collection for a view; read the view and its manual skills before editing and change the data at the source, so one write feeds every view. When the work is a comparison, a set of options, a checklist, a plan, a backlog or any state that keeps changing, offer a view proactively, naming what the person could DO there, and build it when they accept or the request plainly needs a surface. For a single fork that needs one answer, use the decision_view skill.

THE FEED IS WHERE THE DAY REACHES THE PERSON. Every workspace starts on the For you feed (the view `for-you`; if the person archived it, a card reaches no one, so tell them another way), and Par's own AI does not write it: the person's own AI does, which here is you. When something deserves their attention outside this conversation (a pull request waiting for them, a message to answer, a deadline, a result you finished), put it in front of them as a card in `feed_items`, and pick up what they ask for from a card in `feed_requests`. Load the par_feed skill (manage_skill find, query: "par_feed") before writing the first card: it carries the card shape, the request queue and how to learn from `feed_feedback`.

WRAP-UP SWEEP. Before ending non-trivial work, check whether any agreed decision, correction, preference, relation, grounded interpretation or reusable method stayed only in the chat. Save what the PRECEDENCE step allows, drop the noise, and confirm what you DID, not what you will do. Do not use Par Box unless explicitly asked.
